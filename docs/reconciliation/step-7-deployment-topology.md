# Step 7 — Deployment topology assessment

- **Status:** Assessed 2026-10-02; the current repository-native pilot topology is observed, while Flight Deck deployment and authority migration remain unselected
- **Scope:** [Reconciliation plan Step 7](../RECONCILIATION_PLAN.md#step-7--flight-deck-deployment-topology), the landed [G004-001 pilot](../../.mission-control/README.md), and the proposed [Step 6 event contract](step-6-event-contract.md)
- **Authority boundary:** [Mission Control concepts](../guides/mission-control-concepts.md) govern the method; [canonical-reference notes](canonical-reference-notes.md) distinguish optional Flight Deck product choices from this repository's implementation

## Finding

The current useful topology is small: versioned Markdown contracts and state in this repository, Git for provenance, GitHub Actions for check facts, Codex reading local context, and Erik for protected decisions. It served one editorial goal. There is no Flight Deck application, event store, Mission Log projection, external-system adapter, or demonstrated need to relocate authority. A separate Flight Deck planning checkout was reviewed read-only for this assessment. It remains a documentation-first bootstrap and defers its first product slice, stack, data model, and deployment architecture. Its plans are useful product inputs, not an installed service or governing source for this repository; its source files are not copied or linked here.

Step 7 therefore records the **as-operated topology** and conditional migration choices. It does not select a Flight Deck deployment, storage technology, synchronization mechanism, permissions model, or Step 8 portfolio demo. “Deployment topology” here locates logical authority and physical access; it does not imply that each primitive needs a separately deployed service.

## What the other Flight Deck checkout changes—and does not

The separate checkout's current-state and product-thesis documents leave M000 and the first product slice open. They value project context, durable objects, and re-entry, while saying Flight Deck and Mission Control can stand independently. Its provenance guidance treats the bundled architecture stack as advisory. No code or topology there proves a Flight Deck integration with this repo.

That checkout's bootstrap operating model calls GitHub a temporary control plane and uses “Flight Deck” both for a methodology-area label and for the product. Its glossary describes a Mission Profile; the newer [operating model](../mission-control-reference/mission-control-operating-model.md) centers a versioned Goal Contract plus mutable Goal State. These historical terms are useful design history, but should not be copied into a new runtime as equivalent objects without reconciliation.

The imported [Flight Deck product-boundary reference](../mission-control-reference/flight-deck-product-boundary.md) says the product may own governed engineering-change state while specialist tools retain raw records. That is a **conditional product ambition**, not a rule that this pilot's Contract or State must move out of Git. The newer [authority clarification](canonical-reference-notes.md#governing-clarification) permits Flight Deck, specialist tools, or a combination to fulfill the method. No application stack or Flight Deck Runtime / Control Plane / Experience service split follows from those labels.

| Other existing-tool federation                     | Connect an issue/document system, Git, CI, and human operating practice without Flight Deck.                                                                                                                                             | Methodologically valid; no specific external system is selected or integrated in this repository.                                                                | A real team/use case and existing tool permissions make this the lower-cost way to satisfy the same contracts.                                        |

The key migration rule is **one write authority per primitive and version**. A Flight Deck view may derive or cache current state, but its displayed value must carry source version, observation time, and uncertainty. If it later becomes authoritative for a primitive, the handoff must name the cutover point and how stale clients, corrections, lost connectivity, duplicate actions, and rollback are handled. Agent access is scoped to its permitted read/write operations, never inferred from a broad user credential or an available API.

## Decisions needed before implementation

1. **Step 8 product outcome:** Is the next portfolio slice Flight Deck, an implementation assistant, a Lab workflow, or a combination? The separate Flight Deck repo has not yet chosen its first user-facing mission. This Step 7 record does not make that choice.
2. **First consumer and question:** Identify who needs a view or action beyond the current documents and GitHub UI, what they cannot reliably determine now, and how success will be observed on a second real case. G004-001 alone supplies no latency, blocked-time, or cross-goal reliability baseline.
3. **Authority and data cutover:** For every selected primitive, choose whether Flight Deck is a reader, an approved writer, or the system of record. Define source versioning, permissions, human approval proof, correction, conflict, outage, and exit behavior before a second writer is deployed.
4. **Event adoption:** If aggregate history is in scope, approve the Step 6 schema version, producer identities, storage, access/redaction, retention, deduplication, and replay policy. An event projection must not silently become the Goal State authority.
5. **Physical deployment:** Only after the first product slice and authority choice, select application boundary, hosting, database/queue if demonstrated, integration credentials, and a relevant verification plan. The site and Lab remain independent and do not gain a Flight Deck dependency through this assessment.

**Step 7 result:** The pilot's actual topology and conditional Flight Deck boundaries are recorded for each primitive. The best-supported continuation is the existing repository-native arrangement while a later product goal tests whether a read-only Flight Deck view solves a concrete visibility problem. No Flight Deck deployment, adapter, event runtime, authority migration, or Step 8 demo option has been adopted here.
